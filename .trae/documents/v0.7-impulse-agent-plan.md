# v0.7 冲动消费拦截 Agent 与愿望单系统 实施计划

## 1. 摘要

新增一个独立的「愿望单 / 理财助手」抽屉：

- 后端新增 `impulse_records`（愿望单）与 `impulse_messages`（对话）两张表，`CREATE TABLE IF NOT EXISTS` 免迁移。
- 新增 `/api/impulse` 增删改查，`/api/agent/status`、`/api/agent/chat`、`/api/agent/messages`。
- LLM 通过 `.env` 配置（`dotenv`）：未配置时所有接口返回明确提示，不崩溃，前端禁用输入并提示「请先配置 API Key」。
- Prompt 采用「固定 System + 紧凑 JSON 大盘快照 + 最近 12 条对话 + 最多 10 条待购愿望」的固定上限组合，Token 量级可控。
- Agent 输出严格 JSON：`{ reply, wishlistAction }`，愿望单写入由后端确定性执行，不依赖模型记忆。
- 前端在大盘栏增加「愿望单 / 理财助手」按钮，抽屉上半部分为愿望单列表（含"每天需省 X 元"与冷静期进度），下半部分为聊天框。

```sql
CREATE TABLE IF NOT EXISTS impulse_records (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  item_name    TEXT NOT NULL,
  amount_cents INTEGER NOT NULL,
  status       TEXT NOT NULL DEFAULT 'waiting'
               CHECK (status IN ('waiting','purchased','abandoned')),
  created_at   TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

-- impulse_id 允许 NULL：未关联具体物品的闲聊也存一份
CREATE TABLE IF NOT EXISTS impulse_messages (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  impulse_id INTEGER REFERENCES impulse_records(id) ON DELETE CASCADE,
  role       TEXT NOT NULL CHECK (role IN ('user','agent')),
  content    TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

CREATE INDEX IF NOT EXISTS idx_impulse_messages_impulse ON impulse_messages(impulse_id);
```

### 3.7 Agent 接口：`server/routes/agent.js`（挂载 `/api/agent`）

1. `GET /status` → `{ configured: isLlmConfigured }`。**始终 200**，供前端决定是否禁用输入。
2. `GET /messages?impulseId=` → 该物品最近 50 条消息（`impulseId` 缺省查 `impulse_id IS NULL` 的闲聊）。
3. `POST /chat`：
   - 未配置 → `503 { error: '请先配置 API Key（在项目根目录 .env 设置 LLM_API_KEY 与 LLM_API_URL）' }`。
   - body：`{ message: string, impulseId?: number }`；`message` 去空白后为空 → 400。
   - 组装：`buildSystemPrompt()` + 历史（最近 12 条）+ 用户本次消息；历史来自 `impulse_messages`，按 `impulseId`（缺省 `IS NULL`）过滤。
   - 调模型 → `parseAgentReply`。
   - 若 `action.type === 'add'`：事务内插入 `impulse_records(waiting)`，拿到 `newId`。
   - **事务内同时写入本次 user 与 agent 两条 `impulse_messages`**，`impulse_id = newId ?? impulseId ?? null`。
   - 返回 `{ reply, impulse: 新建项或 null, configured: true }`。
   - 模型调用失败 → `502 { error: '助手暂时不可用：<原因>' }`，**不写库**（避免留下孤立的用户消息）。
4. 提示词只读不写：`buildSystemPrompt` / `buildDashboardContext` 都是纯函数，便于用 `node -e` 直接打印验证体积。

## 4. 三个关键问题

### 4.1 Prompt 如何注入大盘与愿望单，且不超 Token

**结构（三段式，全部有硬上限）**

1. **System（固定，约 400 字）**：
   ```
   你是用户的私人理财助手「守财奴」。你的原则是「劝阻第一，规划第二」。
   1. 先共情，再用数据劝阻：结合给定的大盘（余额、今日结余、待填补超支、本月兴趣预算剩余）说明这笔钱的机会成本。
   2. 若用户仍然坚持，建议把它放进愿望单，并强调 3 天冷静期的作用（到第 3 天再决定）。
   3. 不要编造数据，不要输出 Markdown 表格，回答控制在 150 字以内。
   4. 若用户明确表达想买某物并给出了价格，你必须在 wishlistAction 里填写 add。
   只输出 JSON，不要代码块：
   {"reply":"给用户的话","wishlistAction":{"type":"none"}}
   或
   {"reply":"...","wishlistAction":{"type":"add","itemName":"魔女服","amountYuan":140}}
   ```
2. **Context（用户消息前的一条 `system` 或拼进 user 前缀，约 300~600 字符）**：`buildDashboardContext` 产出的紧凑 JSON，只含标量：
   - 大盘：`today / balance / dailyLimit / todayBalance / outstandingOverBudget / hobby{budget,spent,remaining}`（金额统一转「元」，保留 2 位小数，去掉 `_cents` 噪音）。
   - 愿望单：**仅 `waiting`，最多 10 条**，字段 `id/name/price/daysWaited/cooldownRemaining/dailySaveNeeded`。
   - `currentItem`：当前会话关联的物品（如果用户点选了列表项）。
3. **History（最近 12 条，单条截断 800 字符）**：从 `impulse_messages` 取，只取当前 `impulseId` 会话；超出部分直接丢弃（不做摘要，避免额外一次模型调用和成本）。

**为什么不会爆**：静态 System ≈ 250 tokens，Context 固定字段 + ≤10 条愿望 ≈ 200~350 tokens，历史 12 × 平均 60 tokens ≈ 720 tokens，本次用户消息 ≤ 200 tokens。**最坏约 1500~1800 tokens**，与账本记录数完全解耦。不注入任何当日明细、标签全量、历史月份数据。

**额外保护**：`MAX_MESSAGE_CHARS = 800` 对每条历史与用户输入做 `slice(0, 800) + '…'`；`temperature 0.6`；超时 30s（`AbortSignal.timeout`）。

### 4.2 「每天需要省多少钱」的公式

```
本月剩余天数（含今天） = diffDaysBetween(today, 本月最后一天) + 1
每天需省 = ceil(物品价格 / 本月剩余天数)
```

- 例：今天 2026-11-09，本月 30 天 → 剩余 22 天；魔女服 ¥140 → `ceil(14000 / 22) = 637` 分 = **¥6.37/天**。
- 用「自然月剩余天数」而非固定 30 天，与 v0.6 的兴趣预算同属月度口径，用户容易理解；1 号时约等于整月均摊，月末会显得更贵，正好起到催促作用。
- 全部在**服务端**计算，`GET /api/impulse` 直接返回结果，前端不做重复计算，避免两端口径漂移。
- 向上取整到「分」，保证按这个金额攒够时一定够买。

### 4.3 聊天状态如何管理（Agent 怎么知道要关联到哪件物品）

**核心原则：不依赖模型记忆，全部由后端确定。**

1. **写入靠结构化动作，不靠模型调用工具**：模型被迫输出 `wishlistAction`。后端校验通过后，在**同一个事务**里创建 `impulse_records`，并把本轮 user / agent 两条消息写入 `impulse_messages`，`impulse_id` 指向刚创建的物品。因此「用户说想买 140 的魔女服」→ 物品与这段对话天然绑定，落库即完成关联。
2. **后续对话靠 `impulseId` 显式传递**：前端在请求体里带 `impulseId`（用户点选的列表项；新建后自动选中）。后端用它
   - 过滤历史消息（`WHERE impulse_id = ?`）；
   - 填充 `currentItem` 注入 Prompt，模型知道「现在聊的是哪件、放了几天」。
   没有 `impulseId` 时是自由闲聊，消息以 `impulse_id = NULL` 存储。
3. **前端不维护对话状态机**：发送 → 拉取刷新；切换物品 → 重新 `GET /messages?impulseId=`。刷新页面后历史仍在（都在 SQLite 里）。
4. **异常不污染状态**：模型失败时不写任何消息（返回 502），因此不会出现「用户说了但 Agent 没回」的孤儿记录，也不需要重试/回滚逻辑。
5. **冷静期不额外存字段**：`daysWaited` 由 `created_at` 与今天现算，`cooldownRemaining = max(0, 3 - daysWaited)`，随日期自然递减、跨天自动生效。

## 5. 假设与决策

1. **`.env` 放在项目根目录**（与 `.gitignore` 中已有的 `.env` 一致），由 `server/env.js` 用绝对路径加载，不受工作目录影响。
2. **新增可选 `LLM_MODEL`**：OpenAI 兼容接口必须带 `model`，默认 `gpt-4o-mini`，在 `.env.example` 中注明可选。未配置 Key 或 URL 均视为未配置。
3. **未配置时 `/status` 返 200 + `configured:false`**，`/chat` 返 503；前端据此禁用输入，不发起无效请求。
4. **模型输出必须是 JSON**，但解析采用「整体解析 → 提取首个 `{...}` → 降级为纯文本」三级容错，任何异常都不会 500。
5. **愿望单写入只支持 `add`**：模型只负责识别「想买什么、多少钱」，不做批量更新/删除，避免误改数据；其余操作由 UI 按钮完成。
6. **「放弃」= 软删除**（`status='abandoned'`），保留聊天记录，符合表结构里预置的 `abandoned` 状态；`DELETE` 仅作为误建数据的兜底。
7. **冷静期固定 3 天**，不新增列，不强制拦截购买（未满 3 天点「买下」只做二次确认），避免把用户锁死。
8. **「买下」写入账单时**：金额 = 物品价格、备注 = 物品名、日期 = 今天、类型 = 支出、不带标签，避免自动计入 v0.6 的兴趣预算。
9. **`buildSummary` 上移到 `overview.js`**：让 summary 路由与 Agent 共用同一份大盘口径，杜绝两处数字不一致；`/api/summary` 的响应字段与顺序保持不变。
10. **不引入任何前端状态库 / 不引入 OpenAI SDK**，只用 Node 内置 `fetch`，依赖最小化。

## 6. 验证步骤

前置：`npm run dev` 运行中（3001 / 5173）。

1. **未配置 Key 的降级**
   - 不创建 `.env`（或用空值的 `.env`）→ `GET /api/agent/status` 返回 `{configured:false}`，HTTP 200。
   - `POST /api/agent/chat` 传 `{"message":"我想买魔女服，140块"}` → 503 且 `error` 含「请先配置 API Key」；后端进程不崩溃、无未捕获异常。
   - 浏览器打开抽屉：聊天输入框禁用并显示配置提示；愿望单仍可手动新增/买下/放弃（不依赖 LLM）。
