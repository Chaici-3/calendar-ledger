## Summary

在 v0.2 上增量加入标签能力，范围严格限定：

1. 激活 `tags` 表（补 `is_preset`），预置 `餐饮 / 交通 / 爱好 / 购物 / 其他`，其中 `爱好` 的 `is_preset = 1`

## Proposed Changes

### 1. `server/db.js` — 外键开关、tags 补列与预置、record_tags 建表

**做什么**

- 打开数据库后立即执行 `db.pragma('foreign_keys = ON')`。SQLite 的外键默认可能不生效，级联删除依赖它。
- `tags` 表结构保持 `id / name / created_at`，用迁移补列（不能改已有的 `CREATE TABLE IF NOT EXISTS` 来生效）：
  - `PRAGMA table_info('tags')` 判断无 `is_preset` → `ALTER TABLE tags ADD COLUMN is_preset INTEGER NOT NULL DEFAULT 0`
- 预置标签（幂等，每次启动都执行）：

```sql
INSERT OR IGNORE INTO tags (name, is_preset) VALUES
  ('餐饮', 0), ('交通', 0), ('爱好', 1), ('购物', 0), ('其他', 0);
UPDATE tags SET is_preset = 1 WHERE name = '爱好';
```

  - 顺序按 `id` 递增，正好是「餐饮 → 交通 → 爱好 → 购物 → 其他」，前端胶囊顺序即此
  - 按要求只有 `爱好` 置 1；`UPDATE` 兜底处理「之前已存在同名标签但 is_preset=0」的情况
- 新建关联表：

```sql
CREATE TABLE IF NOT EXISTS record_tags (
  record_id INTEGER NOT NULL REFERENCES records(id) ON DELETE CASCADE,
  tag_id    INTEGER NOT NULL REFERENCES tags(id)    ON DELETE CASCADE,
  PRIMARY KEY (record_id, tag_id)
);
CREATE INDEX IF NOT EXISTS idx_record_tags_tag_id ON record_tags(tag_id);
```

**外键与级联说明（本次重点之一）**

- `record_id → records(id) ON DELETE CASCADE`：删除记录时 SQLite 自动清理该记录的所有关联行，**后端 DELETE 不需要手写清理**；级联由 `foreign_keys = ON` 保证
- `tag_id → tags(id) ON DELETE CASCADE`：虽然 v0.3 没有删标签的接口，但把方向也定义好，避免以后留下孤儿关联
- 复合主键 `(record_id, tag_id)` 自带唯一约束，天然防止同一记录重复关联同一标签；它同时是 `record_id` 方向的索引，所以只需额外给 `tag_id` 建索引
- 建表必须在 `db.js` 里完成（早于 routes 里的 `db.prepare`），否则启动即报 `no such table`

### 2. `server/routes/tags.js`（新）— 只读标签列表

**做什么**

**为什么单独一个文件**：`records.js` 已经 180+ 行，标签列表是独立资源，单文件单职责，符合现有 `routes/` 组织方式。

### 4. `server/routes/records.js` — tags 读写 + 避免 N+1

**(a) 查询侧：固定 2 条 SQL，与记录条数无关**

新增 `attachTags(rows)` 帮助函数：

1. 记录列表走原来的 `listStmt` / `listByDateStmt`（1 条 SQL）
2. 若 `rows` 非空，收集 `ids`，用一条 SQL 批量取关联：

```sql
SELECT rt.record_id, t.name
FROM record_tags rt
JOIN tags t ON t.id = rt.tag_id
WHERE rt.record_id IN (?, ?, ...)
ORDER BY t.id ASC
```

3. 在 JS 里用 `Map<recordId, string[]>` 分组，再交给 `toRecord(row, tags)` 输出

**为什么不是 N+1**：无论当天 1 条还是 100 条记录，都只有 **2 条查询**；相比「每条记录查一次标签」线性增长，这是常量级。`IN` 的占位符按本次 id 数量动态拼、`db.prepare` 按请求构建，比预编译缓存更简单，且 better-sqlite3 的 prepare 开销可忽略。

单条记录（POST/PATCH 的响应）用独立预编译语句 `tagsByRecordStmt`（`WHERE rt.record_id = ? ORDER BY t.id`），1 条 SQL 直接取 `string[]`。

不用 `GROUP_CONCAT`：标签名可能含逗号，`string[]` 语义会被破坏。

**(b) 写入侧：查/建标签 + 事务**

- `normalizeTags(raw)`：
  - 不是数组 → 400 `{ error: 'tags 必须是字符串数组' }`
  - 元素必须 string → 否则 400；`trim()` 后丢弃空串；按首次出现顺序去重
  - 单个名称 > 20 字符 → 400；单记录 > 10 个标签 → 400（防止脏输入，不做更多规则）
- `resolveTagIds(names)`：
  - `INSERT INTO tags (name, is_preset) VALUES (?, 0) ON CONFLICT(name) DO NOTHING`（预编译）
  - 再 `SELECT id FROM tags WHERE name = ?` 取 id
  - 依赖 `name` 的唯一索引实现「查/建」，无需先 SELECT 再判断；已存在的预置标签会直接命中，不会被重复插入
- `replaceRecordTags(recordId, names)`：`DELETE FROM record_tags WHERE record_id = ?` + 逐条 `INSERT OR IGNORE INTO record_tags (record_id, tag_id)`，语义是**整体替换**
- **事务**：把「写 records + 写 record_tags」包进 `db.transaction(...)`（better-sqlite3 同步事务），任何一步失败整体回滚，不会出现「记录存了但标签半套」的中间态
- `POST /`：`tags` 缺省视为 `[]`；校验通过后在同一事务里插入记录 + 解析标签 + 写关联；响应里带 `tags`
- `PATCH /:id`：
  - 增加 `hasTags = body.tags !== undefined`，并纳入「没有需要更新的字段」的判断
  - 金额/备注沿用现有分支；`tags` 出现则整体替换
  - 金额/备注的 UPDATE + 标签替换放进同一事务
  - 响应同样带最新 `tags`
- `DELETE /:id`：**代码不变**，级联由外键完成（`foreign_keys = ON` 是前提）
- `toRecord(row, tags)` 增加 `tags` 字段；`GET /` 两条分支都走 `attachTags`
- 旧记录没有关联行时返回 `tags: []`，前端无需特殊处理

### 5. `client/src/App.jsx` — 标签 state 与多选 UI

**state 设计（本次重点之一）**

```js
const [availableTags, setAvailableTags] = useState([]);   // GET /api/tags：[{ id, name, isPreset }]
const [selectedTags, setSelectedTags] = useState([]);     // 新增表单：选中的标签名 string[]
const [customTag, setCustomTag] = useState('');           // 新增表单：自定义输入框
const [draftTags, setDraftTags] = useState([]);           // 行内编辑：草稿标签名 string[]
```

- 选项一律用**标签名**做 state，不用 id：接口契约就是 `tags: string[]`，自定义标签在保存前还没有 id，用名字可以统一「已有标签」和「待创建标签」
- 选中集合用数组而不是 Set：React 需要新引用才能触发重渲染，数组的 `includes/filter` 足够，且能直接 `JSON.stringify` 给接口
- 选择/取消：

```js
const toggleTag = (name, list, setList) =>
  setList(list.includes(name) ? list.filter((t) => t !== name) : [...list, name]);
```

- 胶囊数据源 = 已有标签 ∪ 当前选中：`缺省的自定义标签在保存前不在 availableTags 里，也要能显示成已选胶囊`
- 挂载时 `GET /api/tags`；仅在选择日期变化时不需要重取；**新建成功后重取一次** `availableTags`（让新自定义标签进入可选池），编辑不产生新标签，不必重取
- `customTag` 输入框：`onKeyDown` 里判断 `Enter` → `preventDefault()`（避免触发表单提交）→ trim 非空则加入 `selectedTags` → 清空输入；不在表单里提交，避免误加空标签
- 新增表单提交 body：`{ amount, date: selectedDate, tags: selectedTags }`；成功后清空 `amount` 与 `selectedTags`
- 列表项展示：在备注旁渲染 `record.tags.map(...)` 为胶囊，data 来自接口的 `tags: string[]`
- 行内编辑：
  - `startEdit` 额外 `setDraftTags(record.tags)`
  - 编辑区在金额/备注输入行下方追加一行胶囊（可选标签 = `availableTags ∪ draftTags`），点击切换
  - `saveEdit` body 增加 `tags: draftTags`；`cancelEdit` 清空 `draftTags`
- 标题改为「记账本 v0.3」
- 不改日期/合计/删除逻辑

## Assumptions & Decisions

| 项 | 决定 | 理由 |
|---|---|---|
| `is_preset` | 只 `爱好 = 1`，其余 0 | 按需求原文；给兴趣预算留标记 |
| `is_hobby` | 不自动联动，选择「爱好」标签不写 `records.is_hobby` | 未要求，避免隐藏副作用 |
| 标签顺序 | 按 `tags.id ASC`（预置顺序固定，自定义追加在后） | 胶囊顺序稳定 |
| 标签 API 形状 | `{ tags: [...] }`，单条记录 `tags: string[]` | 沿用现有响应风格 |
| 自定义标签 | 前端提供胶囊 + 输入框；后端按名查/建 | 否则 v0.3 无法产生自定义标签 |
| 编辑标签语义 | `PATCH` 带 `tags` 时**整体替换**，不带则不动 | 与行内编辑的直觉一致 |
| 重复标签 | trim + 去重（保序），空串丢弃 | 容错且不写脏数据 |
| 标签上限 | 名称 ≤ 20 字符、单记录 ≤ 10 个 | 边界校验，不扩展更多规则 |
| 删除记录 | 依赖 `ON DELETE CASCADE`，不写手删逻辑 | 数据库保证一致性 |
| 无用标签 | 不自动清理自定义标签 | 后续可复用；v0.3 无删标签接口 |
| 查询策略 | 列表固定 2 条 SQL（记录 + 批量关联） | 避免 N+1；不用 `GROUP_CONCAT` 防名字含逗号 |
| 事务 | 记录写入 + 标签关联写入放同一事务 | 防止半写状态 |
| 依赖 | 无新增包 | SQLite 原生支持所需能力 |

## Verification

1. **迁移**
   - `PRAGMA table_info(tags)` → 含 `is_preset`，`notnull=1`，默认 `0`
   - `SELECT name, is_preset FROM tags ORDER BY id` → 恰好 5 条：餐饮/交通/爱好/购物/其他，仅爱好为 1（重复重启不重复插入）
   - `PRAGMA foreign_key_list(record_tags)` → `record_id→records.id`、`tag_id→tags.id` 且 `on_delete=CASCADE`
   - `PRAGMA foreign_keys` → `1`
2. **接口**
   - `GET /api/tags` → 5 条，字段 `isPreset`
   - `POST /api/records {"amount":"12","tags":["餐饮","爱好","餐饮"]}` → 201，返回 `tags: ["餐饮","爱好"]`（去重）
   - `POST /api/records {"amount":"5","tags":["新标签"]}` → 201，`GET /api/tags` 出现「新标签」且 `isPreset:false`
   - `POST` 不传 tags → `tags: []`
   - `GET /api/records?date=<今天>` → 每条都带 `tags`，顺序与写入一致
   - `PATCH /api/records/:id {"tags":["交通"]}` → 返回只剩 `["交通"]`；`{"tags":[]}` → 清空
   - `PATCH {amount}` 不带 tags → 标签不变（整体替换只在传入时发生）
   - 负例：`tags:"餐饮"`（非数组）、`tags:[123]`、11 个标签、21 字符标签名 → 均 400
   - `PATCH {}` → 仍为 400
3. **级联**
   - 新建一条带 2 个标签的记录，`DELETE /api/records/:id` → 204；查 `record_tags` 中该 `record_id` 的行数为 0，而 `tags` 表里的标签仍在
4. **N+1 自检**
   - 同一天造 5 条带标签记录后请求列表，日志/计数确认关联查询只执行 1 次（按代码结构应为固定 2 条 SQL，与条数无关）
5. **前端验收**（http://localhost:5173）
   - 胶囊显示 5 个预置标签；多选/取消选中态正确
   - 自定义输入框输入「咖啡」回车 → 出现已选胶囊；保存后列表显示该胶囊，`GET /api/tags` 中出现「咖啡」
   - 保存后新增表单清空金额与选中标签
   - 列表记录在备注旁显示标签胶囊；无标签记录不显示占位
   - 行内编辑切到另一组标签并保存 → 列表与合计刷新，标签被整体替换
   - 编辑取消 → 标签不变
   - 删除带标签的记录 → 列表消失，无报错（级联生效）
6. **回归**：日期切换、合计、金额校验、备注编辑与 v0.2 行为一致；`is_hobby` 未被改动
