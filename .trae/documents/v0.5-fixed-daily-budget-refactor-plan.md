# v0.5 重构 — 每日固定限额与超支弥补机制

## Summary

废弃 v0.5 的生存目标逻辑（`initial_balance` / `survival_start_date` / `survival_end_date` / `dailyMinBudget` / 余额÷剩余天数），改为单一配置 `daily_max_budget`，并用「按日期顺序的结余填补队列」计算哪些历史日期仍处于超支未平状态。

最终能力：

1. 设置只有一个字段：每日最大可支配开销（分）。
2. 总余额 = 全部收入 − 全部支出（不再有初始资金）。
3. 逐日：净开销 > 每日额度 → 产生超支；净开销 < 每日额度 → 省下的钱按 FIFO 填补最早的历史超支。
4. `GET /api/summary` 返回总余额、今日结余、每日固定额度、待填补超支总额、`overBudgetDates`。
5. 前端大盘展示上述数据；时间轴 / 日历继续按 `overBudgetDates` 标红，超支被填平后自动撤红。
6. 边界：不做生存目标归档、不做预期收入。

不修改标签、时间轴滚动、日历翻月、记录 CRUD、行内编辑等既有逻辑。

## 关键口径（开工前请确认）

用户原文两处描述存在矛盾，本计划按可自洽的口径实现，集中说明如下：

1. **Net Expense 的方向**
   原文写「Net Expense = 当天总收入 − 当天总支出」，同时又说「收入大于支出时当天结余为正，可抵消之前超支」，且「Net Expense > 每日额度 → 超支」。若按原文公式，收入越高越容易超支，与「收入可抵消」矛盾。
   **本计划采用：`Net Expense = 当日总支出 − 当日总收入`（净流出）。** 收入会降低净开销；收入大于支出时净开销为负，当天不仅不超支，还会产生「每日额度 + 净收入」的结余用于填补。

2. **空白天是否算「省下钱」**
   **本计划采用：算。** 从最早记账日到今天，按自然日遍历；没有记录的日期净开销按 0，等于省下整个每日额度。
   实现上不会逐日循环：SQL 只取有记录的日期，日期之间的空白天按天数批量折算结余（`空白天数 × 每日额度`）。
   副作用：如果用户长期不记账，会累积较大的结转结余，新的超支可能立刻被历史结余抹平。这是「每天固定额度可结转」的自然结果。

3. **省下的钱是否有结转池**
   **本计划采用：有。** 每次结余先按 FIFO 填补队列中最早的超支；队列填空后，剩余结余进入结转池（buffer），后续新出现的超支优先用结转池抵扣，抵扣不完的部分才进入队列并保持红色。
   这样「先省后花」与「先花后省」都能正确衔接，最终未填补金额等价于累计（额度 − 净开销）为负的部分。

4. **每日额度为 0 视为未设置**
   `daily_max_budget = 0` 时跳过整套超支计算：`outstandingOverBudget = 0`、`overBudgetDates = []`，前端提示「未设置每日额度 / 去设置」。避免新用户一打开就全部标红。

### 3. `server/overview.js` — 重写为超支队列引擎（重点）

**放置位置：SQL 负责按日聚合，JS 负责顺序填补。** 不用纯 SQL 的递归 CTE：FIFO 队列 + 结转池是有状态过程，SQL 递归实现可读性差且难以验证；而按日聚合后，JS 循环只遍历「有记录的日期」，复杂度可控。

#### 3.1 查询

```sql
SELECT date,
       SUM(CASE WHEN type = 'income' THEN -amount_cents ELSE amount_cents END) AS net_expense
FROM records
WHERE date <= ?
GROUP BY date
ORDER BY date ASC
```

- 一天多条记录（收入 + 支出）在 SQL 中合并成 `netExpense = 支出 − 收入`。
- `? = todayLocal()`：未来日期不参与「截至今天」的超支队列。
- 最早记录日就是第一行；没有记录直接返回空结果。

#### 3.2 填补算法（JS 伪代码）

```js
// B = dailyMaxBudget（分）
// queue: [{ date, amount }]，FIFO，只存尚未填平的日期
// buffer: 已填平队列后剩余的结余，可结转给后续超支

function applySavings(amount) {
  while (amount > 0 && queue.length > 0) {
    const head = queue[0];
    const used = Math.min(amount, head.amount);
    head.amount -= used;
    amount -= used;
    if (head.amount === 0) queue.shift();   // 这一天恢复常规状态（撤红）
  }
  buffer += amount;                          // 队列已空，剩余结余结转
}

function applyDeficit(date, amount) {
  const used = Math.min(buffer, amount);
  buffer -= used;
  amount -= used;
  if (amount > 0) queue.push({ date, amount });
}

let prevDate = null;
for (const row of dailyRows) {
  if (prevDate !== null) {
    const emptyDays = diffDaysBetween(prevDate, row.date) - 1;
    if (emptyDays > 0) applySavings(emptyDays * B);
  }

  if (row.netExpense > B) applyDeficit(row.date, row.netExpense - B);
  else applySavings(B - row.netExpense);

  prevDate = row.date;
}

// 最后一个记录日到今天之间（含今天）的空白天
const emptyDaysAfter = diffDaysBetween(prevDate, today);
if (emptyDaysAfter > 0) applySavings(emptyDaysAfter * B);

return {
  outstandingOverBudget: queue.reduce((sum, item) => sum + item.amount, 0),
  overBudgetDates: queue.map((item) => item.date),
};
```

要点：

- `netExpense > B` 的差额进入队列；`netExpense < B` 的差额先补最早队列，再进结转池。
- 同一天可能先出现赤字、后被后续结余部分填补，`amount` 递减；只有降到 0 才从队列移除，因此「部分填补」的日期保持红色。
- 结转池保证「11-01 省 100、11-02 超 80」不会把 11-02 标红（历史结余当场抵扣）。
- 空白天批量折算，不按自然日逐天循环。

#### 3.3 导出接口

```js
export function splitTotals(rows) {...}          // 保留，收入/支出总额
export function getBalance() {...}               // { settings, totals, currentBalance }
```

## Assumptions & Decisions

| 项 | 决定 | 理由 |
|---|---|---|
| Net Expense | 支出 − 收入（净流出） | 原文公式与「收入可抵消」矛盾，按可自洽口径实现 |
| 空白天 | 计为省下整份额度 | 「每天固定额度、按自然日遍历」；SQL 取有记录日 + 批量折算，避免逐日循环 |
| 结转 | 填完队列后剩余结余进 buffer，可抵后续超支 | 累计视角自洽，先省后花不吃亏 |
| 队列顺序 | FIFO，先填最早超支 | 符合「优先填补队列里最早的超支」 |
| 部分填补 | 保留日期，金额递减，仍标红 | 未填平即维持提醒 |
| B = 0 | 视为未设置，不做超支计算 | 避免初始状态全部标红 |
| 历史预算 | 当前 B 回溯应用到全部历史 | settings 无版本历史；本版不做预算生效日期 |
| 未来记录 | 计入总余额，但不进入截至今天的队列 | 队列明确「到今天」；余额反映全部账面 |
| 旧 settings key | 读取忽略，PUT 时事务内删除 | 懒迁移，不改表结构、不主动破坏数据 |
| records 的 isOverBudget | 移除 | 统一由 summary 提供；前端未使用，避免重复全量计算 |
| 初始资金 / 生存目标 | 全部移除 | 用户明确废弃 |

## Verification

### 1. 设置

- 空库 `GET /api/settings` → `{ settings: { dailyMaxBudget: 0 } }`。
- `PUT { dailyMaxBudget: 10000 }` → 再 GET 一致；`settings` 表只剩 `daily_max_budget`，旧 key 被删除。
- 负数 / 小数 / 非数字 → 400；缺省或 `null` → 0；重复 PUT 覆盖不累加。

### 2. 队列算法（B = ¥100，测试后清理数据）

- **纯超支**：11-03 支出 180、11-04 支出 120 → 队列 `[11-03:80, 11-04:20]`，`outstanding=100`，两日均红。
- **后续结余填补**：11-05 收入 120、支出 20 → 当天结余 200，先填 11-03 的 80，再填 11-04 的 20；`outstanding=0`、`overBudgetDates=[]`。
- **空白天结转**：11-01 支出 180（赤字 80），11-02 无记录（省 100）→ 11-01 被填平；11-03 支出 150 → 用剩余 20 抵，队列 `[11-03:30]`。
- **部分填补**：11-03 赤字 80，11-04 结余 40 → `outstanding=40`，`overBudgetDates=["2026-11-03"]`。
- **收入抵扣**：当天收入 300、支出 100（净 −200）→ 当天不超支，并产生 300 结余。
- **未来记录**：11-20 支出 500 不计入队列与标红，但计入 `currentBalance`。
- **边界**：无记录 → 0/[]；`B=0` → 0/[]；最早记录日之前的日期不产生额度。

### 3. 前端

- 设置弹窗只有「每日最大可支配开销」；保存后大盘立即更新。
- 大盘：总余额、每日固定额度、今日结余正确；有待填补时显示红字金额，填平后消失。
- 时间轴与日历对 `overBudgetDates` 中的日期红字浅红底；日期被填平后自动撤红。
- 增删改记录、切换日期、打开日历、标签行内编辑无回归。
